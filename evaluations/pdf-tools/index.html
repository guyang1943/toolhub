PDF 工具横评：本地处理的 BentoPDF vs 功能最全的 Stirling-PDF

两个开源 PDF 工具箱代表两条路线：BentoPDF 坚持浏览器本地处理，Stirling-PDF 用功能广度取胜（官方演示站为服务器处理）。加上「上传型在线 PDF 站」作为反面参照，一次说清怎么选。

结论：含敏感信息的文档（合同、证件、报表）：只用 BentoPDF 这类本地处理工具；功能缺口大且文档不敏感：可以试 Stirling-PDF，优先考虑自托管。

对比项

BentoPDF（浏览器本地 · 隐私：完全本地）

优势：合并/拆分/压缩/旋转/加水印全部本地完成；MIT 协议，可自托管；无广告无注册，打开即用

短板：单文件体积上限受浏览器内存限制；极特殊编码的 PDF 偶尔解析失败

Stirling-PDF（服务器处理（可自托管） · 隐私：官方站需上传）

优势：功能最全：OCR、压缩、转 Word、签名、比较；MIT 协议，Docker 一键自托管；自托管后功能与数据都在自己手里

短板：用官方演示站等于把 PDF 传到别人服务器；功能多，界面学习成本高；自托管需要一台服务器

上传型在线 PDF 站（常见模式）（上传到服务器 · 隐私：需上传）

优势：批量、无需等待本地加载；移动端体验通常更好

短板：文件上传即失控：保留策略、访问日志全是黑盒；免费额度限制 + 广告；处理含隐私文档等于裸奔

详细解读

PDF 是办公场景里最常「交给第三方」的文件类型——转格式、合并、压缩，大多数人顺手就用了搜索排名第一的在线站。这篇横评想拦住的正是这个习惯：PDF 里装的往往是合同、报表、证件扫描件，是全机器最不该外传的文件类型之一。

BentoPDF 的路线是把 pdf-lib 这类库整个搬进浏览器，所有操作在本地完成。实测合并 5 个各 2MB 的 PDF，耗时约 2-3 秒，和上传派把文件传上去再等排队的时间差不多——本地派唯一的门槛是首次加载 WASM 引擎的那一两秒。功能覆盖日常 80% 需求：合并、拆分、压缩、旋转、页面提取、加水印。

Stirling-PDF 走的是「功能无上限」路线，OCR、PDF 转 Word、文档比较这些重活它都能干，但官方演示站是服务器处理——你上传的每一页都在对方机器上过了一遍。它的正确用法是 Docker 自托管：公司和团队在内网跑一个实例，功能全、数据不出内网，这是最理想的形态。个人用户没有服务器的话，就退而求其次用 BentoPDF。

上传型站点的商业模式决定了它必然要留住用户：免费额度、登录墙、广告，以及说不清道不明的文件保留策略。用它处理不敏感的公开文档没问题，但只要文件里有身份证号、银行信息、未公开的经营数据，就不存在「用完即删所以没事」这个选项——上传的那一刻数据已经离开你的信任边界。

结论按场景给：敏感文档 → BentoPDF；内网团队 → 自托管 Stirling-PDF；公开文档 + 冷门功能 → 上传型站点可以偶尔用，用完清空浏览记录。
