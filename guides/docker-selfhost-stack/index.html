一台小主机跑起五个自建服务

一份 Compose 文件管住密码库、备忘、监控、日志和稍后读：数据在自己盘上，升级一条命令。

教程 / 一台小主机跑起五个自建服务
难度 中等约 60 分钟风险 中最后核对 2026-11-26
自建服务最容易死在「第二个服务」：第一个装得顺利，第二个开始端口冲突、第三个忘了数据卷、第四个升级时把旧数据覆盖了。真正需要学的不是某个软件的安装命令，是把它当成一套东西来管——所有服务放在一个目录下，每个服务一份 Compose 片段，数据挂在固定路径，密码走环境变量，升级和回滚是一条命令。这篇按这个结构搭五个最常用的：Vaultwarden（密码库）、Memos（碎片笔记）、Uptime Kuma（在线监控）、Dozzle（看容器日志）、Linkding 或任意一个稍后读。跑起来之后，加第六个只是在目录里多一个文件。

为什么值得折腾

  • 数据在自己手上。密码、笔记这些内容，托管在别人服务器上就等于「取决于它还开多久」——自建服务关停、改名、开始收费的例子每年都有。
  • 一台 4GB 内存的小主机够用。这五个服务加起来常驻内存约 600MB–1GB，剩下的留给系统和缓存。
  • 运维成本可以压到接近零：Compose 负责启动顺序和重启策略，一份备份脚本覆盖全部数据目录，升级就是 pull + up。

开工前要有的

  • 一台能 24 小时开着的小主机：旧笔记本、迷你主机、NAS 都行。2 核 CPU、2GB 内存起步，4GB 更稳。
  • 装好 Linux 并能 SSH 登录（Ubuntu Server 或 Debian 最省事）。不会装就先看站内那篇旧电视盒子改成服务器，思路一样。
  • 一块专门存数据的磁盘或分区，挂载点固定（比如 /srv/data）。数据卷不要放在系统盘的家目录里——重装系统时最容易连数据一起格式化。
  • 一个域名和它的 DNS 管理权限。要在家以外访问、想用 HTTPS，这一步绕不开；只在局域网用可以先跳过，用 IP 访问。
  • 能看懂 docker ps 和 docker logs 的输出。不需要会写代码，但要知道「容器起不来先看日志」。

步骤

  1. 先算清楚机器扛不扛得住

    登录后看两件事：

    free -h
df -h /srv
docker --version

    内存总额低于 2GB 就别硬上五个，先跑密码库和监控两个；磁盘至少留 20GB；/srv 要是独立的挂载点。这一步不是形式——自建服务最常见的死法是第三天磁盘满了，而当时没人看。

  2. 装 Docker 与 compose 插件

    用官方脚本装，不要用发行版仓库里的老版本（compose 子命令和 v2 语法在旧包里没有）：

    curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER

    退出重新登录，让用户组生效，然后确认两条命令都是 v2：

    docker --version
docker compose version

    国内机器拉镜像慢的话，在 /etc/docker/daemon.json 里配一个镜像加速地址再重启 docker。加速地址经常失效，配之前先自己 curl 一下试试能不能拉到。

  3. 定一个目录规矩：一个服务一个文件夹

    所有东西放在 /opt/stack 下面，每个服务一个子目录，数据也放子目录里：

    /opt/stack/
  compose.yaml
  .env
  vaultwarden/data/
  memos/data/
  uptime-kuma/data/
  linkding/data/

    为什么不把数据放到 /var/lib/docker/volumes：那是 Docker 的内部目录，备份要绕一圈，迁移要导出一遍，出事时你分不清哪个卷属于哪个服务。用相对路径挂出来，备份就是 tar 一个目录。

  4. 把密码和域名收进 .env

    compose.yaml 里不写明文密码，全部走环境变量，值放 .env，权限设成 600：

    STACK_DOMAIN=home.example.com
TZ=Asia/Shanghai
VW_ADMIN_TOKEN=换成你自己生成的随机串

    随机串用站内的密码生成器生成 32 位，别用生日和重复字符。.env 不进任何仓库，也不发到聊天工具里——它等于这套服务的总钥匙。

  5. 第一个服务：Vaultwarden（密码库）

    先装这个，因为它最值得自建。compose.yaml 里加：

    services:
  vaultwarden:
    image: vaultwarden/server:latest
    restart: unless-stopped
    environment:
      DOMAIN: https://vw.${STACK_DOMAIN}
      SIGNUPS_ALLOWED: "true"
      ADMIN_TOKEN: ${VW_ADMIN_TOKEN}
    volumes:
      - ./vaultwarden/data:/data

    起它：docker compose up -d vaultwarden，然后 docker compose logs -f vaultwarden 看有没有报错。浏览器打开 http://主机IP:80 注册一个账号，把密码存进去。注册完立刻把 SIGNUPS_ALLOWED 改回 "false" 再 up -d——对外开放注册的密码库，几天内就会被扫描器注册满。

  6. 加监控：Uptime Kuma

    它的作用是「服务挂了有人告诉你」，而不是等你发现。加一个片段：

      uptime-kuma:
    image: louislam/uptime-kuma:1
    restart: unless-stopped
    ports:
      - "3001:3001"
    volumes:
      - ./uptime-kuma/data:/app/data

    起来后进 3001 端口设管理员密码，先加两条监控：本机的 Vaultwarden 地址、以及你家宽带的外网 IP（用 http 探活）。通知渠道选邮件或 Telegram，两者都不需要额外服务。监控要能被外部触发才有意义——只监控「容器进程在不在」的话，容器活着但服务卡死时它不会响。

  7. 加备忘、稍后读和日志面板

    剩下三个都是同样套路，写在同一个 compose.yaml 里：

      memos:
    image: neosmemo/memos:stable
    restart: unless-stopped
    ports: ["5230:5230"]
    volumes:
      - ./memos/data:/var/opt/memos

  linkding:
    image: sissbruecker/linkding:latest
    restart: unless-stopped
    ports: ["9090:9090"]
    volumes:
      - ./linkding/data:/etc/linkding/data

  dozzle:
    image: amir20/dozzle:latest
    restart: unless-stopped
    ports: ["9999:8080"]
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro

    dozzle 挂的是 docker.sock，只读挂载够用，别给写权限。三个都起来后，用一条命令看全部状态：docker compose ps。

  8. 一条命令备份，并验证能恢复

    备份不验证等于没有备份。写一个脚本放 /opt/stack/backup.sh：

    #!/bin/sh
set -e
cd /opt/stack
tar czf /srv/backup/stack-$(date +%F).tar.gz \
  --exclude='./backup' vaultwarden memos uptime-kuma linkding .env
find /srv/backup -name 'stack-*.tar.gz' -mtime +14 -delete

    加执行权限，用 crontab -e 每天凌晨跑一次（cron 表达式可以用站内工具先算一遍再粘）。关键是下一步：把最近的包解到 /tmp 里，确认 vaultwarden/data 下有 db.sqlite3、memos 下有 memos_prod.db。文件在，恢复路径才成立；只看到 tar 包不算。

  9. 升级与回滚：别用 latest 赌运气

    第一次装用 latest 无所谓，长期跑要改成具体版本号（比如 vaultwarden/server:1.32.7），否则某天 pull 下来一个不兼容的大版本，数据迁移一旦失败就回不去了。升级流程固定三步：

    docker compose pull vaultwarden
docker compose up -d vaultwarden
docker compose logs --tail=50 vaultwarden

    回滚就是把镜像 tag 改回上一个版本再 up -d。所以升级前先备份，升级后先看日志再关终端——这两件事的顺序反了，出事时就没有退路。

翻车了怎么办

  • 容器起来就退出：先看 docker compose logs 服务名。最常见是数据目录权限不对（容器内用户没有写权限），chown 一下目录再试；其次是 .env 里变量名写错，日志会明确说缺哪个。
  • 端口被占用：docker compose ps 看有没有旧容器还在跑，或者 ss -lntp 看谁占了端口。改宿主端口（左边那个数字）比杀进程安全。
  • 磁盘满了：docker system df 看镜像和日志占多少，docker image prune 清掉没用的镜像。日志疯长的话，在 compose 里给每个服务加 logging 的 max-size 限制。
  • 全部推倒重来：数据都在 /opt/stack 的子目录里，删掉容器和镜像不会动数据。重新 up 之前确认那三个目录还在，就丢不了。

容易踩的坑

数据没挂出来
只写了 image 和 ports，忘了 volumes。容器删掉重建，数据一起没——而且不会有任何报错提示你。判断标准很简单：这个服务一旦删掉容器，你能不能接受数据消失？不能就必须有 volumes，并且要确认宿主机上真的出现了对应目录。
把所有端口直接开到公网
在路由器上给 3001、5230、9090 都做端口映射，图省事。结果是扫描器几小时内就会找到它们，而这类自建服务的默认配置大多没有防爆破。正确做法是只开一个入口（反向代理 + HTTPS），其余服务只监听 127.0.0.1，或者干脆走内网穿透。
备份放在同一块盘上
tar 包写在 /srv/backup，而 /srv 就是数据盘本身。盘坏的时候，数据和备份一起没。备份至少要落到第二块物理盘、另一台机器或对象存储，三选一，异地那一份才算数。
用 latest 长期跑生产
latest 会在某个凌晨变成一个新大版本。数据库结构迁移是不可逆的，回滚镜像不等于回滚数据。定版本号，升级前备份，这两条能把「某天早上服务打不开」变成「某天早上多花十分钟」。

常见问题

没有公网 IP，也能在外面用吗？
能。用 Cloudflare Tunnel 或 Tailscale 这类内网穿透，不需要在路由器上开端口，也不需要公网 IP。Cloudflare Tunnel 的好处是顺手给了 HTTPS 和域名，站内有一篇专门讲；Tailscale 更简单，装完就是一张虚拟内网，缺点是每台设备都要装客户端。
2GB 内存的机器真的够吗？
五个服务全开大概 600MB–1GB，2GB 能跑但没余量，系统更新或某个服务内存泄漏时会开始用 swap，反应变慢。建议 4GB 起步。不够就先只跑 Vaultwarden 和 Uptime Kuma，这两个加起来不到 200MB。
为什么不用 NAS 自带的应用商店？
自带商店省事，但版本通常落后几个大版本，安全补丁跟得慢，而且换 NAS 品牌时数据迁移路径不透明。Compose 的好处是这套配置在哪台 Linux 上都能跑，换机器就是拷目录 + up。两者不冲突：先在 NAS 上跑 Compose，比在商店里点安装更可控。
docker.sock 挂给 dozzle，会不会有安全风险？
有。能读 docker.sock 就等于能看所有容器信息，只读挂载能阻止它启停容器，但仍然暴露了容器的环境变量。所以 dozzle 不要直接对公网开放，放在反代后面加一层认证，或者只在内网访问。
