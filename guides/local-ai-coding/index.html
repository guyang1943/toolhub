本地模型写代码：补全不出本机

Ollama 起一个代码模型接到编辑器里，什么时候够用、什么时候该换回云端，一次说清。

教程 / 本地模型写代码：补全不出本机
难度 中等约 45 分钟风险 低最后核对 2026-11-26
编辑器里的 AI 补全已经很好用，但它意味着你正在写的东西实时发到别人服务器上。对开源代码无所谓，对客户项目、内部系统、带密钥的配置就不一定了。本地模型是另一条路：模型文件在自己盘上，推理用自己的显卡或 CPU，请求不出本机。代价是能力弱一档、速度慢一些、显存有硬门槛。这篇不吹本地替代云端，而是说清楚分工——哪些活本地做得又快又安全，哪些活本地做不了、老老实实联网。

为什么值得折腾

  • 代码是最不该随便上传的内容之一。它包含业务逻辑、内部地址、偶尔还有硬编码的密钥和测试账号。
  • 本地补全的延迟是稳定的。不走网络，不受高峰时段和别人限流影响，断网也能用。
  • 成本是固定的。一次下载，之后不再按 token 计费；用得越多，单位成本越低。

开工前要有的

  • 一台能跑得动的机器：16GB 内存起步（跑 7B 量化模型），有独立显卡更好（8GB 显存能跑 7B–14B 的量化版本）。
  • 装好 Ollama（Windows/macOS/Linux 都有安装包）。
  • 一个支持自定义 API 地址的编辑器插件：VS Code 上用 Continue 或 Cline，JetBrains 也有对应插件。
  • 对自己的需求有个判断：你要的是「边打字边补全」，还是「选中一段让 AI 改」。两者对模型大小和速度的要求完全不同。

步骤

  1. 先算硬件：显存决定能跑多大的模型

    粗略对照（量化后的模型，4bit 左右）：

    - 3B：约 2GB，8GB 内存的机器能跑，补全够用，复杂任务吃力。 - 7B–8B：约 4–6GB，16GB 内存或 8GB 显存，性价比最高的一档。 - 14B：约 9–10GB，需要 12GB 以上显存或 32GB 内存，代码能力明显更好。 - 30B 以上：消费级显卡基本放不下，除非用 CPU + 大量内存，但速度会慢到不适合交互。

    关键区分：模型能「装进内存」和「跑得够快」是两件事。用 CPU 跑 14B，补全一次要好几秒，体验上就不成立了。补全场景优先小模型快响应，重构场景再用大模型慢一点。

  2. 装 Ollama，拉一个代码模型

    装完先确认服务在跑：

    ollama --version
ollama list

    然后拉模型。代码方向常见的几个系列：qwen 的 coder 版本、deepseek-coder 系列、codellama。具体标签以模型库页面为准，别照抄别人半年前的文章——版本迭代很快，参数和体积都会变：

    ollama pull qwen2.5-coder:7b
ollama run qwen2.5-coder:7b

    run 进去随便问一句「用 Python 写一个读取 CSV 并按列求和的函数」，看响应速度和结果质量。这一步不满意，后面接编辑器也不会满意。

  3. 确认它真的没出网

    本地模型的卖点是隐私，所以要验证，而不是相信。两条命令：

    # 看服务监听在哪
ss -lntp | grep 11434

# 断网后还能不能跑
ollama run qwen2.5-coder:7b "print hello"

    监听地址应该是 127.0.0.1（只本机）而不是 0.0.0.0（整个局域网都能访问）。如果为了给别的设备用而开成 0.0.0.0，至少确认防火墙挡住了外部访问，并且知道这意味着同一网络里的人可以用你的模型。

    注意：模型不出网，不代表插件不出网。有些插件默认开着遥测，会把「你用了什么功能」上报，个别还会上传代码片段用于改进。装完先去设置里把 telemetry 关掉。

  4. 接到编辑器：Continue 的最小配置

    Continue 的配置文件（VS Code 里按 Ctrl+Shift+P 搜 Continue: Open Config）长这样：

    {
  "models": [
    {
      "title": "Qwen Coder 7B",
      "provider": "ollama",
      "model": "qwen2.5-coder:7b",
      "apiBase": "http://localhost:11434"
    }
  ],
  "tabAutocompleteModel": {
    "title": "Qwen Coder 1.5B",
    "provider": "ollama",
    "model": "qwen2.5-coder:1.5b"
  }
}

    关键在第二个配置：**补全用一个更小的模型**。补全要求 200ms 内出结果，7B 模型在没显卡的机器上做不到；1.5B 质量差一些但响应快，用来补「下一行」足够了。聊天/重构再用 7B。这两个分开设，是本地体验好坏的分水岭。

  5. 上下文怎么给：少而准

    本地模型的上下文窗口通常比云端小，塞太多反而更差。有效的做法：

    1. 用 @文件名 精确引用相关文件，不要「把整个 src 目录给它」。 2. 需要改某段代码时，选中它再提问，而不是描述「在第三个函数里」。 3. 贴报错时只贴关键几行，不要整段日志。

    反例：「帮我优化这个项目」——它看不到项目全貌，只会给出泛泛建议。正例：「这个函数在 n>10000 时很慢，数据长这样（贴 10 行），怎么改」。问题越具体，小模型的表现越好。

  6. 什么时候本地不够用

    诚实地说，下面这些场景本地模型大概率让你失望：

    - 需要理解十几个文件的调用关系（上下文不够）。 - 复杂重构（改接口要同步改所有调用方）。 - 需要跑测试、看结果、再改的迭代式任务——这要求模型能调用工具，本地配置麻烦且不稳。 - 陌生框架的冷门 API（小模型的训练数据覆盖不到）。

    这些场景该用云端。判断标准不是「哪个更强」，是「这段代码能不能上传」：不能上传的用本地，能上传的用云端，中间地带用本地先试，不行再脱敏后上传。

  7. 让它跑得住：几条运维常识

    1. 模型占磁盘。一个 7B 模型 4–5GB，试三个就十几 GB。ollama list 看看，不用的 ollama rm 掉。 2. 显存不够时它会自动往内存溢出，速度断崖式下降。跑之前看一眼任务管理器/GPU 占用，别在开着游戏的时候期待它快。 3. 长时间不用会卸载模型，下次调用要重新加载（几秒到十几秒）。可以设置常驻时间，代价是常占内存。 4. 笔记本用电池时性能会被限制，插电跑。

翻车了怎么办

  • 补全一直不出来：先确认 Ollama 在跑（浏览器打开 http://localhost:11434 应该有返回），再看插件的日志；多半是模型名写错或 apiBase 少了 http://。
  • 第一次响应特别慢：模型在加载。等第一次出结果，之后会快很多。如果一直慢，是模型太大，换小的。
  • 显存不够（OOM）：换更小的量化版本，或者把补全模型降到 1.5B。也可以用 CPU 跑，但要有心理准备。
  • 生成的代码明显不对：先怀疑上下文给少了，再怀疑模型太小。同一个问题换 14B 试一次，能立刻判断是「能力不足」还是「提示不清」。
  • 想让局域网里另一台机器也能用：OLLAMA_HOST=0.0.0.0 启动，但要配防火墙规则，只允许内网段访问，别暴露到公网。

容易踩的坑

以为本地就是绝对隐私
模型不出网是真的，但编辑器插件、剪贴板工具、输入法都可能把内容传出去。真正的隐私取决于整条链路上每个环节，而不是模型在哪跑。用之前把插件的遥测关掉，敏感项目里别同时开着会云同步的笔记工具。
用大模型做补全
14B 模型补全一次要两三秒，而你打字时每停一下就触发一次——结果是一直在等，最后索性关掉。补全用小模型，聊天用大模型，这个分工不能省。
把它当成云端模型的等价替代
本地 7B 和云端旗舰在复杂任务上的差距是数量级的，不是「稍差一点」。预期设成「一个不会泄密、能力中等的助手」，用起来才顺；期待它替代云端，每天都会失望。
OLLAMA_HOST 开成 0.0.0.0 又没防火墙
等于把你机器上的模型服务开放给整个局域网甚至公网（如果端口被映射）。Ollama 默认没有认证，任何人都能调用。要共享就限定网段，或者套一层带认证的反向代理。

常见问题

没有独立显卡，值得折腾吗？
值得，但预期要调低。核显或纯 CPU 跑 7B 量化模型，补全大概 1–2 秒一次，用来「解释这段代码」「写个正则」是够的，用来「边打字边补全」会打断节奏。可以先只用它的聊天功能，补全继续关着。
本地模型会把我写的代码用于训练吗？
模型本身不会——推理是纯本地计算，没有回传通道。但要看你下载的模型许可证，以及插件是否有遥测。开源模型（Apache 2.0、MIT 等）通常没有使用限制；个别模型的许可证对商用有约束，用之前看一眼。
能不能让它读整个仓库？
技术上可以（把文件内容拼进提示词），但会撞上上下文窗口，而且小模型在长上下文里容易「忘掉中间」。更实际的做法是用检索：只把相关的几个文件片段给它。Continue 之类的插件支持索引，但本地做索引会吃 CPU，仓库大时要慎重。
笔记本跑起来风扇狂转，正常吗？
正常。推理是持续满载计算，笔记本散热设计不是为这个场景做的。可以把并发调低、限制 GPU 功耗，或者接受它只在插电时跑。长期高负载对机器寿命有影响，别让它连续跑几小时。
