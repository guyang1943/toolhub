静态站也能有自己的 API

站点继续放在 GitHub Pages，另起一个 Worker 接住表单和统计：一个自定义域、一份白名单，构建管线不用动。

教程 / 静态站也能有自己的 API
难度 中等约 45 分钟风险 低最后核对 2026-11-26
纯静态站有一个硬边界：没有任何东西能接收 POST。订阅表单、反馈、访问统计、搜索建议，全都卡在这里。解决办法不是「把整站迁到有服务端的平台」，而是「另起一个很小的 API，让页面去调它」。这条路的成本几乎为零：Cloudflare Workers 免费额度是每天 10 万次请求，静态资源请求不计费；改动面也最小——构建管线、仓库、发布流程一行都不用动，出问题把 DNS 记录一删就回到原状。这篇把它做完，包括最容易翻车的两处：worker.dev 域名在国内不可达，以及跨域 cookie。

为什么值得折腾

  • 不动机器。整站迁移要重配构建、重设缓存、重跑一遍所有测试；加一个 API 只需要部署一个文件、绑一个子域。
  • 免费额度足够。每天 10 万次请求，对一个刚起步的站是几倍到几十倍的余量；静态资源请求免费且不限量，不占这个额度。
  • 可回滚。API 出问题时，前端把开关关掉就退回纯静态，站点不会跟着挂——这一条在只有一个人维护的项目里比性能重要得多。

开工前要有的

  • 站点已经能正常访问（GitHub Pages、Vercel 或任意静态托管都行），并且有自定义域名。
  • 域名能接进 Cloudflare（NS 或子域 CNAME 到 Cloudflare）。这一步是必须的：workers.dev 的默认域名在国内大多不可达。
  • 本机装 Node.js 18 以上，能跑 npx wrangler。不需要 Docker。
  • 想清楚要存什么。只是收事件的话用 KV 或 D1 都行；要按时间查询、要聚合统计，直接上 D1。

步骤

  1. 先划清边界：API 只做静态站做不到的事

    适合放进 API 的：接收 POST（订阅、反馈）、写一份共享数据（统计、留言）、需要密钥的第三方调用（比如把表单转发到邮件服务）。

    不该放进 API 的：任何能纯前端算出来的东西（图片压缩、格式转换、哈希）、静态内容的分发（那本来就该由 CDN 做）、以及需要长时间运行的批处理。判断标准很实际：这段逻辑如果搬到浏览器里也能跑，就不要放到服务端——多一跳网络，多一份账单，多一处会挂的地方。

  2. 建一个最小的 Worker

    新建目录并初始化：

    npm create cloudflare@latest toolhub-api -- --type=hello-world
cd toolhub-api
npx wrangler dev

    它会起一个本地服务，访问 http://localhost:8787 能看到返回。骨架长这样：

    export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname === '/api/ping') {
      return Response.json({ ok: true });
    }
    return new Response('Not Found', { status: 404 });
  },
};

    先只做 ping，把它部署上线、域名绑通，再写业务逻辑。顺序反过来会在「到底是代码错还是域名没通」之间反复猜。

  3. 绑自定义域：这是国内可用性的前提

    部署之后 wrangler 会给一个 xxx.workers.dev 的地址，先别指望它。在国内网络下这个域名经常连不上，而且不是「慢」而是「超时」。

    正确做法是绑自己的子域，比如 api.example.com：在 Cloudflare 后台 Workers → 你的 Worker → Settings → Domains & Routes 里添加 Custom Domain。它会自动建 DNS 记录并签发证书，等一两分钟。

    验证要从「外网」看，不是本机：

    curl -sI https://api.example.com/api/ping | head -5

    返回 200 且带 content-type: application/json 才算通。

  4. 写第一个真接口：收一条 POST

    接收端要把该挡的挡在门外，顺序是：方法 → 内容类型 → 体积 → 字段白名单 → 来源。

    export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname !== '/api/feedback') return new Response('Not Found', { status: 404 });
    if (request.method !== 'POST') return new Response('Method Not Allowed', { status: 405 });
    if (!(request.headers.get('content-type') || '').includes('application/json')) {
      return new Response('Unsupported Media Type', { status: 415 });
    }
    const raw = await request.text();
    if (raw.length > 2048) return new Response('Payload Too Large', { status: 413 });
    let body;
    try { body = JSON.parse(raw); } catch { return new Response('Bad Request', { status: 400 }); }
    const msg = String(body.message || '').slice(0, 500);
    if (!msg) return new Response('Bad Request', { status: 400 });
    await env.DB.prepare('INSERT INTO feedback (ts, message) VALUES (?, ?)').bind(Date.now(), msg).run();
    return new Response(null, { status: 204 });
  },
};

    为什么要先限体积再 JSON.parse：不设上限的话，一个几十 MB 的请求会先把内存打满。免费版的内存上限是 128MB，一次就够它崩。

  5. 前端怎么调：同域优先，跨域要过预检

    最省事的是把 API 放在主域的子域上，并且允许跨域。前端：

    fetch('https://api.example.com/api/feedback', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ message: '...' }),
}).catch(() => {});

    跨域时浏览器会先发 OPTIONS 预检，服务端必须回 CORS 头，否则请求根本不会发出去：

    const CORS = {
  'access-control-allow-origin': 'https://example.com',
  'access-control-allow-methods': 'POST, OPTIONS',
  'access-control-allow-headers': 'content-type',
};
if (request.method === 'OPTIONS') return new Response(null, { status: 204, headers: CORS });

    不要写 *。写死自己的域名，这样别的站就算拿到地址也不能在浏览器里替你发请求。

    如果以后要做登录，跨域 cookie 会被浏览器的第三方 cookie 策略拦（Safari 默认拦，Chrome 也在收紧）。那时候要么把 API 挪到同一个域（用 Worker 同时托管静态资源），要么改用 Authorization 头带 token。这是「先子域、后同域」的迁移点，一开始就该知道。

  6. 数据存哪：KV 与 D1 的分工

    KV 适合「读多写少、按 key 取」：配置、开关、缓存、短链。写入每天 1000 次的上限，不适合记事件流。

    D1 是 SQLite，适合按时间查询和聚合：事件、订阅、留言。免费额度是每天 500 万行读、10 万行写、总共 5GB。

    建表并绑定：

    npx wrangler d1 create toolhub
npx wrangler d1 execute toolhub --remote --file=./schema.sql

    wrangler.toml 里加上 binding 之后，代码里就是 env.DB。注意 D1 的读取额度按扫描行数算——没建索引的查询会很快把额度吃光，时间字段上一定要有索引。

  7. 密钥不进代码，开关能关掉一切

    任何 token、webhook 地址都不能写在 Worker 源码里（源码会进 git，也可能被读）。用 secret：

    npx wrangler secret put MAIL_WEBHOOK

    然后在代码里读 env.MAIL_WEBHOOK。本地调试时用 .dev.vars（记得加进 .gitignore）。

    再留一个总开关：环境变量 API_ENABLED=off 时所有写接口直接返回 204 不落库。出事时改一个变量、等十几秒生效，比回滚一次部署快得多。这个开关应该在第一天就有，不是出事之后再加。

  8. 观测：最少要知道「有没有人用、有没有报错」

    免费版有每天 20 万条日志。最少做两件事：

    1. 每个请求打一行结构化日志（时间、路径、状态码、耗时），出问题时能 grep。 2. 在 Worker 里 catch 住所有异常，返回 500 的同时把错误信息打进日志——不要让它静默失败。

    try { /* 业务 */ } catch (e) { console.error('api_error', url.pathname, e.message); return new Response(null, { status: 500 }); }

    再加一条外部探活：Uptime Kuma 或任意监控，每分钟 GET 一次 /api/ping，失败三次告警。没有这条的话，API 挂了几天你都不知道——前端通常会 catch 掉错误，页面照常显示，功能静默失效。

翻车了怎么办

  • workers.dev 打不开：这是预期行为，不是配置错。绑自定义域，用 curl 从外网验证。
  • 预检请求 403：OPTIONS 分支没写，或者 CORS 头没带上。抓一次 Network 面板里的 OPTIONS 请求，看响应头有没有 access-control-allow-origin。
  • D1 报 no such table：本地建的表没同步到远端。加 --remote 重新执行 schema，或者用 wrangler d1 migrations apply。
  • 突然开始 500：先在 Cloudflare 后台看实时日志，注意免费版的 CPU 时间是每次 10ms——在请求里同步处理大文件或做重计算会超时，逻辑要移到前端或拆成多次请求。
  • 想完全回退：把前端的 API 地址清空、开关关掉，站点立刻回到纯静态；Worker 不删也不会影响访问。

容易踩的坑

把 API 地址写死成 workers.dev
开发时它好用，上线后国内用户全部超时，而你在本地测不出来。第一天就绑自定义域，并且用手机流量测一次。
CORS 写 *
看起来最省事，等于允许任何网站用访客的浏览器调用你的接口。限流是按你账号的额度算的，别人可以拿它当免费后端。写死来源域名，多一个域就多一行。
在 Worker 里做重活
免费版每次调用只有 10ms CPU 时间（网络等待不计）。图片处理、大文件解析、复杂加密都会超时。这些活要么放前端（浏览器算力免费），要么放到有独立超时的服务里。
没有开关，也没有探活
前端 catch 掉了错误、页面看着一切正常，而接口已经挂了三天。这不是假设——静默失败是这类架构最常见的事故形态。开关 + 探活，两样加起来不到二十行代码。

常见问题

这和把整站迁到 Cloudflare 比，哪个好？
看你要做什么。只加一两个接口，独立 Worker 改动最小、可回滚；要做登录、要同域 cookie、要页面和 API 一起发布，整站放 Worker（静态资源 + API 同一份部署）更干净。两者成本几乎一样——静态资源请求在 Worker 上也是免费不限量。区别是运维复杂度：一个域名还是两个域名，一次部署还是两次。
国内访问真的没问题吗？
绑了自定义域之后，访问路径是「用户 → 你的域名 → Cloudflare 边缘」，这个域名是通的。但 Cloudflare 的部分 IP 段在国内质量不稳定，晚高峰可能变慢，且免费版没有中国大陆节点（需要企业版 + 备案）。如果主要用户在国内且对速度敏感，建议实测：用手机流量和几个不同运营商各跑一次。
免费的 10 万次请求够用吗？
按每天 3000 个访客、每人触发 2 次接口调用算，一天 6000 次，是额度的 6%。真正的风险不是正常流量，是被人刷——所以来源白名单、字段体积上限、以及按 IP 或会话的简单限流要一起做。免费额度是按账号算的，被打满时所有 Worker 一起不可用。
需要备案吗？
服务器在境外（Cloudflare 边缘）时，通常不涉及国内 ICP 备案；但如果用国内 CDN 或国内主机做源站，就需要。这一点以服务商的实际要求为准，别照抄别人的经验——它跟着接入方式和机房位置变。
