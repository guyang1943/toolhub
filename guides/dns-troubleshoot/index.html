域名解析不对时，按这四步查

改了 DNS 不生效？分清是缓存、记录写错还是权威服务器没更新，比反复刷新快得多。

教程 / 域名解析不对时，按这四步查
难度 入门约 30 分钟风险 低最后核对 2026-11-26
「我改了 DNS，怎么还是不生效」——这个问题九成不是 DNS 慢，而是三件事之一：记录本身写错了、改的地方不是真正生效的地方、或者你在看本机缓存。DNS 是一个分层缓存系统，每一层都有自己的过期时间，所以「改了立刻生效」在原理上就不成立。这篇给一套固定顺序的排查法：从 NS 开始，逐层往下问，十分钟内能定位到底卡在哪一层。顺带把 A / CNAME / TXT 这几个最容易混的记录讲清楚。

为什么值得折腾

  • 域名问题会伪装成别的问题。站点打不开、证书签发失败、邮件进垃圾箱、小程序校验不通过，根因都可能在一条 TXT 或 CNAME 上。
  • 排查顺序比工具重要。同样是 dig，先问权威服务器还是先问本机，结论完全不同——先问本机只会看到缓存。
  • 改错一条记录的影响面很大。CNAME 和 A 冲突会让整条解析失效，根域写 CNAME 会让 MX 记录一起失效。知道边界再动手。

开工前要有的

  • 知道域名在哪家注册、NS 指向哪家（域名注册商和 DNS 托管商经常不是同一家）。
  • 能改 DNS 记录的后台权限。
  • 一个终端，装了 dig（Windows 可以用 nslookup，或在线工具代替）。

步骤

  1. 第一步：先确认谁在管解析（NS）

    很多「改了不生效」的根源是：你在 A 家改，实际生效的是 B 家。查：

    dig +short NS example.com

    返回的两三行就是真正管解析的服务器。如果它和你改记录的后台不是同一家，改什么都没用。

    常见情况：域名在阿里云注册，NS 却指向 Cloudflare（因为要套 CDN）；或者反过来，NS 早就迁回去了，人还在旧后台改。这一步花十秒，能省掉后面半小时。

  2. 第二步：搞清四种记录的用途，别混用

    A：域名 → IPv4 地址。最基础的一条。 AAAA：域名 → IPv6 地址。有就配，没有不影响。 CNAME：域名 → 另一个域名（别名）。解析时会继续追下去。注意：CNAME 不能和同名的其他记录共存，尤其是 MX 和 TXT。 TXT：任意文本。现在主要用来做域名验证（搜索引擎、证书、邮件），SPF/DKIM/DMARC 也走它。

    判断该用哪个：目标是 IP 就用 A，目标是另一个域名（比如 GitHub Pages 的 username.github.io）就用 CNAME。托管平台给的说明里通常会写明用哪个，照抄比推理快。

  3. 第三步：按「权威 → 公共 → 本机」的顺序问

    这是整套方法的核心。先问权威服务器（数据的源头），再问公共 DNS（缓存），最后才问本机：

    dig @ns1.example-dns.com example.com A +short
dig @1.1.1.1 example.com A +short
dig example.com A +short

    三种结果的组合直接给出结论：

    - 权威就错 → 记录写错了，回去改。缓存没问题，等也没用。 - 权威对、公共错 → 还在缓存期，等 TTL 过期。 - 公共对、本机错 → 只是本机缓存，换网络或清缓存即可，别人看到的是对的。

    不加 @ 的 dig 问的是本机配置的解析器，这一步经常被当成「全世界的现状」，是误判的主要来源。

  4. 第四步：看 TTL，算清楚要等多久

    TTL 是「这条记录允许被缓存多少秒」。改记录之前先看原来的 TTL：

    dig example.com A | grep -A1 'ANSWER SECTION'

    如果原来是 86400（一天），改完最坏情况要等一天。所以正确的做法是**提前降 TTL**：计划迁移前 24 小时把 TTL 改成 300，等旧缓存过期，再做变更，改完再调回去。

    已经改了才发现 TTL 是一天？没有加速办法。所谓「DNS 加速刷新」的服务大多只是帮你问更多节点，改变不了别人家缓存里的旧值。

  5. 高频错误一：根域写 CNAME

    example.com 这个裸域（根域）按规范不能有 CNAME，因为它必须同时承载 SOA 和 NS 记录。有些服务商允许你填，实际是内部做了转换（CNAME flattening），行为随服务商不同。

    后果：邮件收不到（MX 被压制）、部分验证失败。如果托管商要求根域指向某个域名，优先看它是否提供 A 记录或 ALIAS/ANAME 这类方案。

    判断方法：

    dig example.com CNAME +short
dig example.com MX +short

    如果第一条有值、第二条为空，而你本来配了邮箱，那基本就是这个坑。

  6. 高频错误二：@ 和 www 只配了一个

    @ 代表裸域，www 是子域，它们是两条独立的记录。托管平台给的说明里通常要求两条都配：

    A     @    185.199.108.153
CNAME www  username.github.io

    只配 www 的结果是：用户在地址栏敲 example.com 打不开，而 www.example.com 正常；或者反过来，加上 HTTPS 之后其中一个报证书错误。

    验证两条都通：

    dig +short example.com
dig +short www.example.com

    两个都要有结果，且指向正确的地方。

  7. 高频错误三：邮件验证记录写坏格式

    TXT 记录的值如果是 SPF，必须是一行、以 v=spf1 开头，且一个域名只能有一条 SPF（多条会一起失效）：

    v=spf1 include:_spf.example.com ~all

    DKIM 的公钥通常很长，粘贴时容易被换行或空格截断；DMARC 放在 _dmarc.example.com 这个子域上，不是根域。

    验证：

    dig +short TXT example.com
dig +short TXT _dmarc.example.com

    TXT 的值在输出里会被引号分段（因为超过 255 字符会拆开），这是正常的，别自己动手拼。

  8. 查完之后：把结论写进变更记录

    DNS 变更最容易出的事故是「不知道谁在什么时候改了什么」。至少记三行：改了什么记录、改之前的旧值、改的时间和预期生效时间。

    如果站点突然打不开而你没有改过任何东西，先跑一遍前四步——域名过期、NS 被改、记录被误删，都会表现成「网站挂了」，而它们的修法完全不同。域名到期这种事，注册商的续费邮件经常进垃圾箱。

翻车了怎么办

  • dig 命令不存在（Windows）：用 nslookup example.com 1.1.1.1，或者用在线 DNS 查询工具，注意选「权威服务器」那个选项。
  • 所有层都查不到记录：确认记录是不是建在了错误的域名下（比如建在 www 下却查根域），以及是否保存成功。有些后台需要点「发布」才生效。
  • 解析对了但站点打不开：问题已经不在 DNS。接着查端口、证书、以及托管平台的自定义域名是否验证通过。用 curl -I 看返回码，301 到别处说明跳转配错了。
  • 改了 NS 之后全部记录消失：NS 切换等于换了一整套解析数据，新服务商那边必须把旧记录全部重建。切换前先把旧记录导出一份。

容易踩的坑

用本机 dig 判断「全球生效」
本机问的是本地解析器，它可能缓存了几小时前的旧值。判断生效要看权威服务器和至少两个公共 DNS（1.1.1.1、8.8.8.8），而不是自己电脑。
改之前不降 TTL
TTL 一天意味着改完要等一天。正确顺序是提前一天降到 300 秒，等旧缓存全过期再改，改完观察稳定后再调回。反过来做，只能干等。
把 CNAME 和 MX 放在同一个名字下
同名 CNAME 会压制其他所有记录类型，邮件会静默失效——发出去的邮件没人回，但你收不到退信。要指别名又要有邮件，用服务商提供的 ALIAS/ANAME。
以为 DNS 能解决所有「打不开」
解析只是第一步。解析对了还打不开，接下来是端口、防火墙、证书、应用本身。把 curl -v 的输出按层看，比继续折腾 DNS 有效。

常见问题

网站搬家，怎么做到「几乎不停机」？
提前一天把 TTL 降到 300；新服务器先跑起来并用 IP 或临时域名验证通过；然后一次性切换 A/CNAME。切换后旧服务器至少再开一天，因为还有缓存期内的用户会打到旧地址。
为什么别人能打开，我打不开？
大概率是本机或本地运营商的缓存。换手机流量试一次；如果流量下正常，就是你本地解析器的问题，等 TTL 过期或换个 DNS。少数情况是运营商级缓存（透明代理），只能等。
免费 DNS 和付费 DNS 差在哪？
解析速度和稳定性对个人站差别不大。差别在：付费版通常有更快的全网生效、更多的记录数、健康检查与故障转移、以及更细的日志。域名不多、流量不大时，Cloudflare 免费版已经足够，它还顺带给了 CDN 和证书。
域名快到期了，有什么要注意的？
提前续费，别等到期前一周。到期后通常有 30 天左右的宽限期（可赎回但费用高），过期后可能被他人注册，站点、邮箱、验证记录全部跟着丢。开自动续费，并且确认绑定的支付方式还有效。
