测试假数据

造姓名、手机号、邮箱、地址与带校验位的身份证号

关于测试假数据

写测试用例时最容易随手编一个「13800138000」，然后被测系统一校验就崩：号段不存在、身份证校验位不对、地区码是假的。这个工具造的是能过常见校验的假数据——手机号只从已分配的号段前缀里取，身份证按 GB 11643 的 MOD 11-2 算出校验位并使用真实存在的县级行政区划代码，生成后还会自己再验一遍。它同时把边界写在结果区最显眼的位置：所有号码随机生成，仅供测试，不是真实号码，也不承诺零碰撞；邮箱一律落在 RFC 2606 的保留域，误填进注册表单也不会往真人邮箱发信。数据全程只在本机内存里生成。

使用步骤

  1. 选数据类型：可以只造手机号、姓名、邮箱、地址或身份证，也可以一次生成全套字段
  2. 填条数（1–100）和输出格式：每行一个、带表头的 CSV，或 JSON 数组
  3. 点「生成」，先读结果区顶部那条黄色提示——所有号码仅供测试，不是真实号码
  4. 把结果复制进测试用例、CSV 文件或脚本；身份证号可以再贴进站内「身份证校验」工具复核
  5. 需要稳定可复现的数据时，把生成结果存进测试夹具，不要每次运行时重新随机生成

常见错误

把假身份证号拿去实名认证

这是最不该做的事。号码虽然能通过校验位算法，但它不是有权机关签发的身份标识。把它填进任何实名、开户、签约流程都可能违法，结果区那条提示就是为这个写的。

每次跑测试都重新生成数据

随机数据会让断言不稳定：今天通过的用例明天可能因为某个号码恰好落在边界上而失败。生成一次，把结果存成测试夹具文件，让被测逻辑面对固定的输入。

拿它验证完整地址库

工具只保证省市区名称与代码真实，路名和门牌是拼出来的，也没有邮编和经纬度。要测地址解析、行政区划联动或物流可达性，得用真实的地址数据集，这份假数据覆盖不了。

常见问题

生成的手机号能过运营商校验吗？

能过「格式 + 号段」这一层：号码 11 位，前三位取自 2026-11-06 核对过的已分配号段（130–139、15x、16x、17x、18x、19x），不含 154 / 164 这类空段。但后 8 位是随机的，不代表真实放号，也不保证这个号没被真人使用——任何声称「保证不撞号」的假数据生成器都不可信。

身份证号的校验位是怎么算的？

按 GB 11643（等同 ISO 7064 MOD 11-2）：前 17 位分别乘权重 7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2，求和后对 11 取模，用「10X98765432」这串按余数取一位。工具生成完会立刻按同一算法自检，算错就抛错，不把坏数据交给你。

地区码是真实存在的吗？

是。前六位取自 GB/T 2260 里真实存在的市辖区代码（如 110105 北京市朝阳区、440305 广东省深圳市南山区）。这里收录的是常见区县而不是全量表，够用来造能过校验的假数据。街道名与门牌号是编的，不属于行政区划。

为什么邮箱都是 example.com？

example.com / .net / .org 是 RFC 2606 明确保留给文档与示例的域名，不会指向真实收件人。用真实域名造邮箱，一旦测试数据被误塞进注册或邮件接口，就可能给陌生人发信；用保留域可以把这个风险直接消掉。

会不会碰巧生成真实人物的身份证号？

有可能，工具不承诺零碰撞。生日限定在 1970–2005，顺序码优先取 000–009 与 990–999 两端，都是为了把概率压低；但只要编号空间是有限的，随机生成就存在碰撞可能。所以结果区用醒目的黄条标注「仅供测试，非真实号码」，并且这些号码不应用于实名、注册或任何对外用途。
