## 三、每轮的执行步骤

### 0. 前置检查（任何一条不过就停，只输出报告）

```bash
git fetch origin                      # ssh 超时就重试一次，别动密钥
git status --short --branch
git rev-list --left-right --count origin/main...main
node -e "console.log(require('./changelog.json').entries[0].version)"
curl -s https://toolhub.bot.cd/sw.js | grep -m1 'const VERSION'
```

| 检查 | 通过条件 | 不过怎么办 |
|---|---|---|
| 分支 | 在 `main` | 停下报告 |
| 工作区 | 干净（未跟踪的 `.workbuddy/` 不算） | 停下报告 |
| 落后远端 | 落后就 `git pull --ff-only` | 不能快进就停 |
| 版本对齐 | ① `V == W`：正常待发，写新版本；② `V == W+1` 且本文件「当前状态」写着「已构建待推」：上一轮准备好的发版提交，**直接从第 5 步推** | 其余 `V != W` 一律停下报告（有人写了没发，别重复写） |
| 有无内容 | 上一个发版提交之后有真实代码/内容改动 | 没有就报「无待发内容」结束 |
| 改动范围 | 属于当版授权的主题 | 出现授权外的改动（改了工作流逻辑、隐私页文案、既有工具行为）就停 |

本地 `main` **领先** `origin/main` 是正常状态（合并/发版提交还没推），不是异常。

### 1. 定版本号

`W` 的末位 +1（`v3.28 → v3.29`）。**不自己跳号**，也不因为改动多就抬大版本。

### 2. 写 changelog

在 `changelog.json` 的 `entries` 顶部插一条：`{ date, version, items[] }`，**LF 换行**，
保持 `JSON.stringify(…, null, 2)` 的排版（整份文件就是这个格式，写脚本时别改风格）。
`sw.js` 的版本号由 `gen-sw.mjs` 读 `entries[0].version` 派生，不用手改。

**文案体例**（这是本站唯一的对外版本说明，别写成「修复若干问题」）：

- 每条写「**改了什么 + 为什么这么改 + 怎么验证的**」。
- 数字必须**实测**后再写。v3.29 就踩过：交接单写首屏 92.5 KB，实际是 93.4（资源库合集在交接单之后才合并）。
- 教程类按主题归并成 2–3 条即可，不用一篇一条；但要写清「篇数从几变几」。
- 顺手修的旧账也要写，而且要写清「原来的坏法为什么校验抓不到」。

### 3. 构建 + 八套全量（红着不发布）

```bash
npm run build:prod        # 必须带域名；不带会把 robots.txt 写成 dev 域名、全站 URL 写错
npm run check             # 八套 + 三道前置闸门
npm run lint
```

顺序不能反：`verify` 有一条「sw 版本号与 changelog 一致」，所以**先写 changelog 再 build**，
否则它一定红。

`npm run check` 会先跑三道闸门（外链边界字段 / 投稿规范 / 工具脚本语法），
闸门不过就一套都不跑——这三道挡的都是「六套全绿也救不回来」的问题。
**分支上绿不等于合并后绿**：两条分支各改各的 `verify.mjs`，单看都过，合起来可能撞断言。

### 4. 判断哪些产物该带

```bash
git diff --numstat
```

- `llms.txt` / `privacy/index.html` / `robots.txt`：**空 = 只有换行差异，直接还原**；有数字 = 内容真变了，必须带上。
- 构建产物有「多一个空行」的老毛病（每版 180+ 个文件各多 1–2 行空白）。用 `git diff -U0 <file>`
  逐条核验「新增行全是空白」后还原，**别整目录 checkout**（会丢真改动）。不要在发版当口去治成因。
- `sitemap.xml` 的 `lastmod` 与 `feed.xml` 的 `pubDate` 会变成当天，**这是真改动，要带上**。

### 5. 提交并推送

```bash
git add changelog.json perf-budget.json sw.js offline/ changelog/ api/tools.json feed.xml sitemap.xml
# 提交信息写文件，再 git commit -F（不要用 -m 传多行）
git push origin main
```

推的是本地领先的那一批提交（含合并提交），不是单个提交。
报 `ssh.github.com:443 Connection timed out` 就**重试一次**，别动密钥、别改 `~/.ssh/config`。

### 6. 线上探活

```bash
npm run online -- --wait 120
```

`verify-online` 是**三态**：通 / 不通 / 查不到（跳过）。查不到不等于没推上去。
当前 `PATHS` 共 **42 条**（含教程页、`assets/lib/guide-text.js`、五个 TP7 工具页与四个 vendor 文件）。发新页后按需补 1–2 条。

### 7. 收尾

- `README.md` 三处导语数字（中文 / 繁体 / 英文；**英文那句是「本地在前、总数在后」，与另两处相反**）。
- `docs/promotion.md` 里的工具数与内容数。
- `.workbuddy/memory/<日期>.md` 追加本版记录：版本号、提交号、首屏、离线包、测试数、主题与取舍。

## 四、边界（硬规矩）

- **只推 `main`**，不合并分支、不改写历史。
- 前置不过时：**不自己造版本号、不替人合并分支、不顺手带别的改动**。不发就不发。
- 遇审批 / 权限 / SSH 失败：停下，把**原始报错**写进报告；不绕过、不关沙箱、不动密钥。
- 判断拿不准（版本号、文案、某个文件该不该带）：**停下来问**，别猜。
- 八套红着不发布。红了先判断是真问题还是断言本身错了；要改断言，必须单列「为什么这条断言是错的」。

## 五、已知坑

| 坑 | 表现 | 处理 |
|---|---|---|
| `git fetch` / `push` 超时 | `ssh.github.com:443 Connection timed out` | 重试一次；git 全走 SSH 443 |
| 先 build 后写 changelog | `verify` 报「sw 版本号与 changelog 不一致」 | 先写 changelog 再 build |
| 整目录 `git checkout` 产物 | 丢掉 sitemap/feed 的真改动 | 逐文件 `-U0` 核验 |
| 八套并行跑 | browser 偶发 337/338 假红 | 顺序跑；先单跑一次再判回归 |
| `audit` 不给 URL | 打默认端口，静默挂住 | 显式传 `http://127.0.0.1:<port>` |
| 文档里的旧数字 | 照抄交接单写错首屏 | 发版前重跑 `npm run perf`，以实测为准 |
| 版本标签漂移 | T2 的文档里写死了 `v3.30` | 发版时统一回实际版本，别让归档前后不一致 |
