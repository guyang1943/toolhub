# 任务包怎么发出去（交接手册）

这份文档只回答一个问题：**把任务包交给别的工具 / 别人时，到底要递过去什么。**

任务包（`TP1`–`TP5`）本身是说明书，不是可执行的东西。收包方不动手还好，一旦要改代码，光给 markdown 等于给了一张没有图纸的施工单。

---

## 一、先分清两类包

| 类型 | 包 | 交付物形态 | 需要项目代码吗 |
|---|---|---|---|
| **内容型** | TP1 文案补全、TP5 目录扩充 | 一批 `JSON` / 文本片段，或整份改写后的数据文件 | **不需要**。只要给它现有的 JSON 结构和字段说明，它产出内容，我来合并 |
| **代码型** | TP2 移动端适配、TP3 无障碍、TP4 新增工具 | 改过的源文件（CSS / JS / 新工具目录） | **需要**。它得看到真实的 DOM 结构、现有的类名、构建脚本，否则写出来的东西风格和契约都不对 |

这条分界决定了两种发放方式，别混用。

---

## 二、三种发放方式

### 方式 A：只发说明书（仅内容型）

把 `docs/taskpacks/TP1-content.md` 或 `TP5-directory.md` 整份粘给执行方，再补一句「现有数据结构见附件 `articles.json` / `tools/directory.json`」——文件也一起给，因为它要知道字段长什么样。

- 适合：任何网页版 AI、任何不能跑 Node 的地方。
- 交付要求：**完整文件内容**，不要 diff。字段顺序、缩进、换行都按原文件来。
- 我这边的成本：跑一遍 `node scripts/verify.mjs` + `node scripts/build-pages.mjs`，绿了就合并。

### 方式 B：发代码快照（代码型，跨机器 / 跨工具）

执行方拿不到你本机的目录，所以要在包外再塞一份项目副本。用 `git archive` 而不是手打 zip——它只打包**已跟踪文件**，天然排除 `.git/`、`node_modules/`、`.wrangler/`、`.tmp-*` 这些不该给的东西：

```bash
cd toolhub
git archive --format=zip -o ../toolhub-TP2.zip HEAD
```

然后把 `toolhub-TP2.zip` + `docs/taskpacks/TP2-mobile.md` 一起发过去。

对方解开后就能跑验收命令（`node scripts/build-pages.mjs`、`node scripts/verify.mjs`），**先让它跑一遍基线，确认它那边的环境是全绿的**——这一步不做，后面它报的错你分不清是它改坏的还是环境问题。

> 环境要求写进包了：Node 22；`new-tools-test.mjs` 还需要 Python + `pip install "qrcode[pil]"`；`browser-test.mjs` 需要 Chromium（可用 `BROWSER_PATH` 指定）。如果对方跑不了真浏览器测试，就限定它只跑 `verify` / `spa-render-test` / `build-pages`，真浏览器那套留给我这边跑。

### 方式 C：让它直接在这个工作区里跑（代码型，同机）

如果外包方是另一个能访问同一路径的智能体会话（比如另开一个 WorkBuddy 任务），**不用丢文件**——把项目路径和任务包路径给它，允许它读写，但把边界写死：

```
项目：C:\Users\huwei\WorkBuddy\2026-10-20-10-57-11\toolhub
任务：docs/taskpacks/TP2-mobile.md
只许改：assets/style.css、assets/style.tool.css
不许改：任何 .js、任何 .html 结构、scripts/ 下任何文件、perf-budget.json
```

这种方式省事，但有两个真风险：

1. **并发改同一文件**。所以一次只发一个包，或者严格按包里给的「独占文件」清单分发——TP1 和 TP4 都会碰 `articles.json`，这两个**不要同时发**。
2. **它把测试改绿了事**。所以包里那条纪律要重复一遍：测试红了说明有真问题；真要动断言，必须在交付说明里单列一条「为什么这条断言本身是错的」，由我判断。

---

## 三、每个包该用哪种方式

| 包 | 推荐方式 | 原因 |
|---|---|---|
| TP1 内容补全 | A | 交付的是文案与 JSON 字段，不需要碰代码 |
| TP2 移动端适配 | B 或 C | 要改 CSS，得看见真实 DOM 与断点 |
| TP3 无障碍与键盘 | B 或 C | 要改 `app.js` / `tool-page.js`，且要知道现有 aria 约定 |
| TP4 新增三个工具 | B 或 C | 要按 `docs/TOOL-CONTRACT.md` 建目录、写 manifest、跑 lint |
| TP5 目录扩充 | A | 纯数据补充，但要自己验证 URL 可用 |

---

## 四、交接时一定要带上的四样东西

1. **任务包本身**（`TPx-*.md`），整份，不要节选。
2. **它要读的输入文件**。包里「先读这些」那节列了清单，把文件一起给——只给路径而对方看不到文件，等于没给。
3. **这份手册**，特别是「三条通用纪律」和「验收命令」两节。
4. **交付格式**：见下。

## 五、要求对方怎么交回来

固定成这三件，缺一件我就退回：

1. **改动的完整文件**（整份内容，不是 diff / patch / 片段）。新建的文件要给出完整相对路径。
2. **`交付说明.md`**：改了哪些文件、每个文件为什么改、有没有偏离任务包要求的决定及理由。
3. **验收命令的原始输出**：它跑过的命令、退出码、通过数。

diff 一律不收。原因很实在：这个仓库每天在变，patch 的上下文行对不上就是一场手工排错，而整文件替换能一眼看出谁改了什么。

---

## 六、我这边收包后做什么

1. `git status` 看它到底动了哪些文件——和交付说明对不上的，先问清楚。
2. 跑全量：`build-pages` → `verify` → `spa-render-test` → `new-tools-test` → `perf-budget` → `smoke-test` → `browser-test` → `audit`。
3. 过了就合并，然后按惯例更新 `changelog.json` / `README.md` / `ROADMAP.md` 与资料库两份文档。
4. 没过就带着具体报错退回去，不动它改的东西。

---

## 七、可以直接粘给执行方的一段话

> 你在参与一个零依赖的静态工具站项目 ToolHub 的其中一个任务。
>
> 任务说明书：`docs/taskpacks/TP2-mobile.md`（先完整读一遍，包括末尾的验收命令）。
> 项目根目录：解压后的 `toolhub/`。
>
> 三条硬纪律：
> 1. 只改说明书里「独占的文件」那一节列出的文件。其他文件一律不动，需要改就在交付说明里说明理由，由我来改。
> 2. 不要为了让测试变绿去改测试。测试红了先判断是真问题还是断言本身错了，后者要在交付说明里单列一条论证。
> 3. 不要加第三方依赖，不要手改构建产物（`index.html`、`*/index.html`、`sw.js` 都是生成的）。
>
> 开工前先跑一遍基线：`node scripts/build-pages.mjs && node scripts/verify.mjs`，确认全绿再动手。
> 交付三件套：改动后的完整文件、`交付说明.md`、验收命令的原始输出。
